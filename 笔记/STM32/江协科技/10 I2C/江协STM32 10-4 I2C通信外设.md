# 10-4 I2C 通信外设

> [!abstract] 这一集只解决一个问题
> **STM32 芯片内部那个硬件 I2C 外设到底长什么样？为什么用它就得按「事件」来编程？**
>
> 答：把 10-3 里 CPU 一位一位手动做的活儿（抬 SCL、摆 SDA、收应答）全部交给硬件电路，CPU 退到「在关键节点等一个标志位、到了就做下一步」的位置上。这些关键节点就是**事件 EVx**：`EV5`（起始位已发出）、`EV6`（地址已发出/被应答）、`EV8`/`EV8_2`（发送数据）、`EV7`（收到数据）。库函数把它们打包成 `I2C_EVENT_*` 宏，用 `I2C_CheckEvent()` 去等。
>
> 上一集 [[江协STM32 10-3 软件I2C读写MPU6050]] ｜ 下一集 [[江协STM32 10-5 硬件I2C读写MPU6050]] ｜ 章索引 [[江协STM32 10 I2C（章索引）]]

## 1 软件 I2C 与硬件 I2C：活儿交给谁

| 要做的事 | 10-3 软件 I2C | 10-4 / 10-5 硬件 I2C |
| --- | --- | --- |
| 产生 SCL 时钟 | `MyI2C_W_SCL(1/0)` + `Delay_us(10)` 手动翻 | I2C 外设的**时钟控制**电路按 `CCR` 自动生成 |
| 起始 / 终止条件 | `MyI2C_Start` / `MyI2C_Stop` 手动摆 SDA | `I2C_GenerateSTART` / `I2C_GenerateSTOP` 一句话 |
| 收发一个字节 | `MyI2C_SendByte` / `MyI2C_ReceiveByte` 循环 8 次 | `I2C_SendData` / `I2C_ReceiveData` 写读 DR，移位由硬件做 |
| 收发应答位 | `MyI2C_SendAck` / `MyI2C_ReceiveAck` | 硬件自动收发；`I2C_AcknowledgeConfig` 只决定「要不要应答」 |
| CPU 要做什么 | 全程盯着每一位 | 只在**事件**处等标志、做下一步动作 |
| 引脚 | 任意 GPIO，自己挑 | 固定复用（I2C2 → PB10/PB11） |
| 代码量 | 要自己写 `MyI2C.c` | 工程里**没有** `MyI2C.c` 这个文件 |

课件 Slide 140 的原话：

> STM32 内部集成了硬件 I2C 收发电路，可以由硬件自动执行时钟生成、起始终止条件生成、应答位收发、数据收发等功能，减轻 CPU 的负担
> 支持多主机模型
> 支持 7 位 / 10 位地址模式
> 支持不同的通讯速度，标准速度（高达 100 kHz），快速（高达 400 kHz）
> 支持 DMA
> 兼容 SMBus 协议
> STM32F103C8T6 硬件 I2C 资源：I2C1、I2C2

## 2 硬件 I2C 外设框图

课件 Slide 141 给的是参考手册 **图242「I²C 的功能框图」**。把它按「数据走哪条路、时钟谁管、状态谁记」拆开看：

| 框图中的方块 | 作用 |
| --- | --- |
| `DATA REGISTER`（数据寄存器 DR） | CPU 读写的入口：要发的字节写这里，收到的字节从这里读 |
| 数据移位寄存器 | 把 DR 里的 8 位**一位一位**送上 SDA，或把 SDA 上的一位一位拼成 8 位送回 DR |
| 数据控制 | 控制 SDA 线上「发」还是「收」，以及起始终止条件的产生 |
| 比较器 + 自身地址寄存器 / 双地址寄存器 | 从机模式下，把总线上来的地址和自己地址比对，决定要不要应答 |
| 帧错误校验（PEC）计算 / PEC 寄存器 | SMBus 用的包错误校验，本课不用 |
| 时钟控制 + 时钟控制寄存器（CCR） | 按 `CCR` 设置生成 SCL 的时钟 |
| 控制寄存器（CR1&CR2） | 总开关、使能位、中断使能等 |
| 状态寄存器（SR1&SR2） | 记录「现在到哪一步了」——**事件判断就是读它俩** |
| 控制逻辑电路 | 把上面这些串起来，并对外给出「中断」「DMA 请求与响应」 |
| `SMBALERT` | SMBus 的告警线，本课不用 |

课件 Slide 142「I2C 基本结构」的文字版更直白，一句话就是数据通路和时钟通路各一条：

```text
数据通路：  数据寄存器 DR ──► 移位寄存器 ──► 数据控制器 ──► SDA
时钟通路：  时钟控制器 ──► SCL
开关控制 / GPIO
```

### 2.1 本课真正会碰到的寄存器

| 寄存器 | 课件里的叫法 | 本课通过什么库函数碰它 |
| --- | --- | --- |
| `DR` | 数据寄存器 DR | `I2C_SendData()` / `I2C_ReceiveData()` |
| `CR1` / `CR2` | 控制寄存器（CR1&CR2） | `I2C_Cmd()`、`I2C_AcknowledgeConfig()`、`I2C_GenerateSTART()`、`I2C_GenerateSTOP()`、`I2C_ITConfig()` |
| `SR1` / `SR2` | 状态寄存器（SR1&SR2） | `I2C_CheckEvent()` / `I2C_GetFlagStatus()` 内部读的就是它俩 |
| `CCR` | 时钟控制寄存器（CCR） | `I2C_Init()` 里的 `I2C_ClockSpeed`、`I2C_DutyCycle` |
| `OAR1` / `OAR2` | 自身地址寄存器 / 双地址寄存器 | `I2C_Init()` 里的 `I2C_OwnAddress1`、`I2C_OwnAddress2Config()` |

`I2C_InitTypeDef` 的成员与它们一一对应（`stm32f10x_i2c.h` 第 50~69 行）：

（上面这段是 `stm32f10x_i2c.h` 第 50~69 行的原文，注释是库自带的英文，未做改动。）

> 参考手册的 I2C 寄存器列表里还有 `TRISE`（上升时间）和 `FLTR`（滤波）等寄存器，但**课件 Slide 141 的框图与 Slide 142 的文字里都没有标出它们**，所以本页不展开。库里的 `I2C_Init()` 会按 `I2C_ClockSpeed` 自己算 `TRISE`，调用者不用管。

## 3 为什么硬件 I2C 要按「事件」编程

硬件 I2C 的工作方式像一个**状态机**：CPU 发出一个动作（比如「产生起始」），硬件开始干活；干完了会置一个状态位；CPU 必须**等这个位**，才能做下一个动作。这个「状态位组合」就叫做**事件（Event，写作 EVx）**。

课件 Slide 143（参考手册 **图245 主发送器传送序列图**）和 Slide 144（**图246 主接收器传送序列图**）把每一步该等哪个事件画得很清楚。图下的原话是：

> 说明：S = Start（起始条件），Sr = 重复的起始条件，P = Stop（停止条件），A = 响应，NA = 非响应，EVx = 事件（ITEVFEN = 1 时产生中断）。

### 3.1 主机发送（写方向）的事件

| 事件 | 出现位置 | 状态位（图245 原话） | 该做什么（图245 原话） |
| --- | --- | --- | --- |
| `EV5` | `S` 之后 | `SB = 1` | 读 `SR1` 然后将**地址写入 DR 寄存器**将清除该事件 |
| `EV6` | 地址 + `A` 之后 | `ADDR = 1` | 读 `SR1` 然后**读 SR2** 将清除该事件 |
| `EV8_1` | 第一个数据之前 | `TxE = 1` | 移位寄存器空、数据寄存器空，**写 DR 寄存器** |
| `EV8` | 每发完一个数据字节后 | `TxE = 1` | 移位寄存器非空、数据寄存器空，**写入 DR 寄存器将清除该事件** |
| `EV8_2` | 最后一个数据之后 | `TxE = 1`、`BTF = 1` | **请求设置停止位**。`TxE` 和 `BTF` 位由硬件在产生停止条件时清除 |
| `EV9` | 10 位地址模式 | `ADD10 = 1` | 读 `SR1` 然后写入 DR 寄存器将清除该事件 |

图245 还有两条注：

> 注：1 – EV5、EV6、EV9、EV8_1 和 EV8_2 事件**拉长 SCL 低的时间**，直到对应的软件序列结束。
> 　　2 – EV8 的软件序列必须在当前字节传输结束之前完成。

第一条注就是「按事件编程」能成立的底气：**在这些事件上硬件会把 SCL 拉低不放（时钟拉伸），一直等你把该做的软件动作做完**，所以 CPU 慢一点也不会丢数据。

### 3.2 主机接收（读方向）的事件

| 事件 | 出现位置 | 状态位（图246 原话） | 该做什么（图246 原话） |
| --- | --- | --- | --- |
| `EV5` | `S` / `Sr` 之后 | `SB = 1` | 读 `SR1` 然后将地址写入 DR 寄存器将清除该事件 |
| `EV6` | 地址 + `A` 之后 | `ADDR = 1` | 读 `SR1` 然后读 `SR2` 将清除该事件。在 10 位主接收模式下，该事件后应设置 `CR2` 的 `START = 1` |
| `EV6_1` | 第 1 个数据 + `A⁽¹⁾` 之后 | **没有对应的事件标志** | 只适于接收 1 个字节的情况。恰好在 `EV6` 之后（即清除了 `ADDR` 之后），要**清除响应和停止条件的产生位** |
| `EV7` | 每收到一个数据字节后 | `RxNE = 1` | 读 DR 寄存器清除该事件 |
| `EV7_1` | 最后一个数据之后 | `RxNE = 1` | 读 DR 寄存器清除该事件。**设置 ACK = 0 和 STOP 请求** |
| `EV9` | 10 位地址模式 | `ADD10 = 1` | 读 `SR1` 然后写入 DR 寄存器将清除该事件 |

对照 10-3 的软件版：软件版读完最后一个字节要手动 `MyI2C_SendAck(1)`（非应答）再 `MyI2C_Stop()`；硬件版这两步就是图246 里的 `EV6_1` / `EV7_1`。

### 3.3 事件 → 库宏 → 库里的值

库函数不让你直接拼状态位，而是把「状态位组合」定义成了 `I2C_EVENT_*` 宏（`stm32f10x_i2c.h` 第 319~389 行）：

| 事件 | 库宏 | 值 | 注释里的状态位 |
| --- | --- | --- | --- |
| `EV5` | `I2C_EVENT_MASTER_MODE_SELECT` | `0x00030001` | BUSY, MSL and SB flag |
| `EV6`（发送） | `I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED` | `0x00070082` | BUSY, MSL, ADDR, TXE and TRA flags |
| `EV6`（接收） | `I2C_EVENT_MASTER_RECEIVER_MODE_SELECTED` | `0x00030002` | BUSY, MSL and ADDR flags |
| `EV8` | `I2C_EVENT_MASTER_BYTE_TRANSMITTING` | `0x00070080` | TRA, BUSY, MSL, TXE flags |
| `EV8_2` | `I2C_EVENT_MASTER_BYTE_TRANSMITTED` | `0x00070084` | TRA, BUSY, MSL, TXE and BTF flags |
| `EV7` | `I2C_EVENT_MASTER_BYTE_RECEIVED` | `0x00030040` | BUSY, MSL and RXNE flags |
| `EV9` | `I2C_EVENT_MASTER_MODE_ADDRESS10` | `0x00030008` | BUSY, MSL and ADD10 flags |

> [!warning] 库里没有 `EV8_1`、`EV6_1`、`EV7_1` 这三个宏
> 官方代码里也没有单独去等它们：
> - `EV8_1` / `EV8` 都用 `I2C_EVENT_MASTER_BYTE_TRANSMITTING` 覆盖；
> - `EV6_1` / `EV7_1` 用「**在等 EV7 之前就把 ACK 关掉、把 STOP 排上**」这个写法一次性顶掉（见 10-5 的 `MPU6050_ReadReg`）。

## 4 `I2C_CheckEvent()` 与函数调用顺序

### 4.1 函数原型与返回值

```c
ErrorStatus I2C_CheckEvent(I2C_TypeDef* I2Cx, uint32_t I2C_EVENT);
```

`ErrorStatus` 只有两个值：**`SUCCESS`**（事件已发生）和 **`ERROR`**（还没发生）。`stm32f10x_i2c.h` 第 310~318 行对 EV5 的说明就是模板：

> After sending the START condition (`I2C_GenerateSTART()` function) the master has to wait for this event. It means that the Start condition has been correctly released on the I2C bus.

### 4.2 它内部到底做了什么

库实现（`stm32f10x_i2c.c`）的顺序是：

```c
flag1 = I2Cx->SR1;
flag2 = I2Cx->SR2;
flag2 = flag2 << 16;
lastevent = (flag1 | flag2) & FLAG_Mask;
if ((lastevent & I2C_EVENT) == I2C_EVENT)
  status = SUCCESS;
else
  status = ERROR;
```

三件事必须看懂：

1. 它是把 **`SR2` 左移 16 位**后与 `SR1` 拼成一个 32 位数——所以事件宏的值才会长成 `0x0003xxxx`、`0x0007xxxx` 这种样子（高 16 位来自 `SR2`，低 16 位来自 `SR1`）。
2. 判断条件是 **`(lastevent & I2C_EVENT) == I2C_EVENT`**，即「要求的位全都为 1 就算成功」，多出来的位不管。
3. **读 `SR2` 本身就会清掉 `ADDR` 标志**——这正是图245/图246 里「读 `SR1` 然后读 `SR2` 将清除该事件」的硬件行为。

> [!warning] 不要改用 `I2C_GetFlagStatus()` 一个个查标志
> `stm32f10x_i2c.h` 第 624~636 行专门写了 `I2C_GetFlagStatus()` 的局限：
> - 调用它会访问状态寄存器，而**有些标志是「读一下就清」**，所以查一个标志可能把别的标志也清掉；
> - 一个事件往往由多个标志组合而成，用单标志查可能得调用两次以上。
>
> 所以课程里等事件统一用 `I2C_CheckEvent()`。

### 4.3 主机发送 / 接收的动作顺序

把图245、图246 翻译成库函数调用，就是 10-5 里 `MPU6050.c` 的骨架：

**写寄存器（对应图245）**

```text
I2C_GenerateSTART(ENABLE) ──► 等 EV5   I2C_EVENT_MASTER_MODE_SELECT
I2C_Send7bitAddress(..., Transmitter) ──► 等 EV6   I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED
I2C_SendData(寄存器地址) ──► 等 EV8   I2C_EVENT_MASTER_BYTE_TRANSMITTING
I2C_SendData(数据) ──► 等 EV8_2  I2C_EVENT_MASTER_BYTE_TRANSMITTED
I2C_GenerateSTOP(ENABLE)
```

**读寄存器（对应图246，中间还有一次重复起始）**

```text
I2C_GenerateSTART(ENABLE) ──► 等 EV5   I2C_EVENT_MASTER_MODE_SELECT
I2C_Send7bitAddress(..., Transmitter) ──► 等 EV6   I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED
I2C_SendData(寄存器地址) ──► 等 EV8_2  I2C_EVENT_MASTER_BYTE_TRANSMITTED
I2C_GenerateSTART(ENABLE) ──► 等 EV5   I2C_EVENT_MASTER_MODE_SELECT      ← 重复起始
I2C_Send7bitAddress(..., Receiver) ──► 等 EV6   I2C_EVENT_MASTER_RECEIVER_MODE_SELECTED
I2C_AcknowledgeConfig(DISABLE)          ← 对应 EV6_1：提前清除响应产生位
I2C_GenerateSTOP(ENABLE)                ← 对应 EV7_1：提前申请停止条件
等 EV7   I2C_EVENT_MASTER_BYTE_RECEIVED
Data = I2C_ReceiveData()
I2C_AcknowledgeConfig(ENABLE)           ← 恢复应答，避免影响后续多字节读取
```

注意写方向的第二个字节等的是 `EV8_2`（不是 `EV8`）——因为它是本次传输的最后一个字节，`EV8_2` 意味着数据**已经真的发到总线上了**，此时再 `STOP` 才安全。库注释（第 362~372 行）也说：`EV8_2` 更慢但更可靠，尤其适合「停止条件之前的最后一次数据传输」。

写方向等待 EV8_2 还有一个前提：`I2C_EVENT_MASTER_BYTE_TRANSMITTED` 要求 `BTF = 1`，而 `BTF` 在 **`DR` 和移位寄存器都空**时才置位。如果代码里连发两个字节，第一个字节只等 `EV8` 就够了；等最后一个字节才用 `EV8_2`。

## 5 硬件 I2C 与软件 I2C 的取舍

课件把两者的能力都摆出来了，取舍其实就是几件事：

| 维度 | 软件 I2C（10-3） | 硬件 I2C（10-5） |
| --- | --- | --- |
| 占 CPU | 每一位都要 CPU 干活，还要 `Delay_us` 空转 | 时序由硬件生成，CPU 只等事件 |
| 引脚 | **随便挑**，还能同时模拟好几路 I2C | **固定复用**：I2C2 = PB10/PB11（I2C1 默认为 PB6/PB7） |
| 速率 | 靠延时凑，改起来简单但不好精确 | 由 `CCR` 精确分频，可 100 kHz / 400 kHz |
| 多主机 | 要自己处理总线仲裁，很麻烦 | 支持多主机模型（课件 Slide 140） |
| 调试 | 逻辑分析仪一看就懂，出错好查 | 卡在某个事件上时不好定位，所以要靠超时保护 |
| 代码 | 多一个 `MyI2C.c` | 少一个 `MyI2C.c`，但多了一堆「等事件」 |

官方 10-2 工程的做法能给一个很实在的提示：**它给「等事件」专门写了一个带超时的函数**——

```c
void MPU6050_WaitEvent(I2C_TypeDef* I2Cx, uint32_t I2C_EVENT)
{
	uint32_t Timeout;
	Timeout = 10000;									//给定超时计数时间
	while (I2C_CheckEvent(I2Cx, I2C_EVENT) != SUCCESS)	//循环等待指定事件
	{
		Timeout --;										//等待时，计数值自减
		if (Timeout == 0)								//自减到0后，等待超时
		{
			/*超时的错误处理代码，可以添加到此处*/
			break;										//跳出等待，不等了
		}
	}
}
```

官方在注释里留了「超时的错误处理代码，可以添加到此处」的空位。**这说明硬件 I2C 的等待是有可能等不到、必须设保护的**——不设超时的话，一旦某个事件不来，程序就死在 `while` 里。这一点在软件 I2C 版本里不存在（软件版根本没有等待循环）。

> [!warning] 关于「硬件 I2C 的坑」，官方材料里能查到什么
> 本页能作为依据的只有两条：① 课件 Slide 140 列出的硬件 I2C 能力清单；② 官方 10-2 源码里那个手工写的超时等待函数。
> **课件与官方源码中未见**对「STM32 硬件 I2C 有哪些已知缺陷 / 为什么后来反而要用软件模拟」的成段说明，所以本页不写这类结论，已列入「待核对」。

## 6 中断与 DMA 方式

- 课件 Slide 140 明确写了硬件 I2C **支持 DMA**。
- 课件 Slide 141 的框图（图242）右下角有两个对外输出：**「中断」**和 **「DMA 请求与响应」**——说明这两种搬运方式硬件本身就准备好了。
- 图245 / 图246 的说明里写着「`EVx` = 事件（**`ITEVFEN = 1` 时产生中断**）」——`ITEVFEN` 是 `CR2` 里的事件中断使能位，也就是说：**同一套事件，既可以轮询等，也可以开中断让硬件来喊你**。
- 库函数方面，`stm32f10x_i2c.h` 里有对应的开关：`I2C_ITConfig()`（第 546 行）、`I2C_DMACmd()`（第 538 行）、`I2C_DMALastTransferCmd()`（第 539 行）；中断源枚举包含 `I2C_IT_EVT`（事件）、`I2C_IT_BUF`（缓冲）、`I2C_IT_ERR`（错误）等（第 210~235 行）。

**但本课的官方代码用的是轮询**：`MPU6050.c` 里是 `while (I2C_CheckEvent(...) != SUCCESS)` 死等，没有配置 NVIC、没有写 `I2Cx_IRQHandler`、也没有用 DMA。课件里也没有给出中断/DMA 版的 I2C 代码。

## 7 易错点

- [ ] 把「事件 EVx」当成中断号 → 事件是**状态位的组合**，轮询时等它、开 `ITEVFEN` 时才变成中断，两者不是一回事。
- [ ] `I2C_CheckEvent()` 的返回值当成布尔用反 → 它是 `ErrorStatus`：`SUCCESS` 才是「等到了」，判断要写 `!= SUCCESS` 或 `== SUCCESS`，别写成 `if (I2C_CheckEvent(...))` 就以为是等到了（`SUCCESS` 的值是 1，这里侥幸能对，但语义上要写清楚）。
- [ ] 不等事件就急着发下一个字节 → 上一步的硬件动作还没做完，数据直接丢。
- [ ] 最后一个字节用 `EV8` 而不是 `EV8_2` 就 `STOP` → 数据可能还没真正发出去，从机收到的是残缺字节。
- [ ] 接收时忘了「**在等 EV7 之前**就把 `I2C_AcknowledgeConfig(DISABLE)` 和 `I2C_GenerateSTOP(ENABLE)` 写好」→ 等读完最后一个字节再操作就已经晚了，从机会继续输出下一个字节（对应图246 的 `EV6_1` / `EV7_1`）。
- [ ] 单字节读完之后忘了 `I2C_AcknowledgeConfig(ENABLE)` 恢复应答 → 后面再做多字节读取时全部收不到数据。官方代码专门加了这一步，注释是「为了不影响后续可能产生的读取多字节操作」。
- [ ] 用 `I2C_GetFlagStatus()` 逐个查标志去替代 `I2C_CheckEvent()` → 读状态寄存器会顺带清掉某些标志（库注释里明确警告过），结果越查越乱。
- [ ] 以为硬件 I2C 也能随便选引脚 → 硬件 I2C 的 SCL/SDA 是**复用功能**，I2C2 固定 PB10/PB11（`引脚定义` 表：PB10 = `I2C2_SCL`、PB11 = `I2C2_SDA`）。
- [ ] 忘了 `I2C_Cmd(I2Cx, ENABLE)` → `I2C_Init()` 只是配置，不使能外设根本不工作。
- [ ] 等事件不设超时 → 一旦某个事件不来就死循环。官方代码用 `Timeout = 10000` 自减跳出。
- [ ] 主机模式下忘了配 `I2C_AcknowledgedAddress` / `I2C_OwnAddress1` 也是必须给的成员 → 从机模式下才有效，但结构体成员不能漏填。

## 8 自测

1. 硬件 I2C 的 `EV5` 对应哪个状态位？该做什么动作才能清掉它？库里的宏叫什么？
2. `EV6` 在发送方向和接收方向分别对应哪个库宏？为什么必须**读 SR2** 才能清掉它？
3. `I2C_CheckEvent()` 的返回值是什么类型、有哪些取值？它内部读寄存器的顺序是什么？
4. 为什么读寄存器时，`I2C_AcknowledgeConfig(I2C2, DISABLE)` 和 `I2C_GenerateSTOP(I2C2, ENABLE)` 要写在**等 EV7 之前**？
5. 图245 的两条注里说 `EV5`、`EV6`、`EV8_1`、`EV8_2` 会「拉长 SCL 低的时间」，这条性质对写代码有什么用？

> [!success]- 参考答案
> 1. `EV5` 对应 `SB = 1`（起始条件已正确发出到总线，课件 Slide 143 图245 原话）。动作是「读 `SR1`，然后把从机地址写入 `DR` 寄存器」（写成库函数就是先 `I2C_CheckEvent` 内部的读 SR1/SR2，再 `I2C_Send7bitAddress()`）。库里的宏是 `I2C_EVENT_MASTER_MODE_SELECT`，值 `0x00030001`（BUSY、MSL、SB）。
> 2. 发送方向是 `I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED`（`0x00070082`），接收方向是 `I2C_EVENT_MASTER_RECEIVER_MODE_SELECTED`（`0x00030002`）。必须读 `SR2` 是因为 `ADDR` 标志「读 `SR1` 然后读 `SR2` 才清除」（图245/图246 原话）；而 `I2C_CheckEvent()` 内部正好就是先读 `SR1`、再把 `SR2` 左移 16 位拼上，所以调用它本身就把 `ADDR` 清掉了。
> 3. 返回类型是 `ErrorStatus`，取值 `SUCCESS` / `ERROR`。内部顺序是：读 `SR1` → 读 `SR2` → `SR2` 左移 16 位 → 与 `SR1` 相或并屏蔽得到 `lastevent` → 判断 `(lastevent & I2C_EVENT) == I2C_EVENT`，成立返回 `SUCCESS`。
> 4. 因为硬件 I2C 在**接收最后一个字节的过程中**就要知道「我应答不应答」和「我什么时候发停止条件」。图246 里 `EV6_1` 是「恰好在 `EV6` 之后（即清除了 `ADDR` 之后）清除响应和停止条件的产生位」，`EV7_1` 是「读 DR 后设置 ACK = 0 和 STOP 请求」。如果在等完 `EV7`、读走数据之后再关 ACK、再发 STOP，从机早就把下一个字节推上 SDA 了，主机又还在应答，时序就收不住。所以官方代码把这两个动作提到 `MPU6050_WaitEvent(EV7)` **之前**。
> 5. 说明在这些事件上硬件会**把 SCL 拉低不放（时钟拉伸）**，一直等到对应的软件序列做完。所以 CPU 处理得慢一点也不会丢数据——「按事件编程」才成立。反过来，`EV8` **不在**这个名单里，图245 的注 2 特别说明「`EV8` 的软件序列必须在当前字节传输结束之前完成」，即发下一个字节要抓紧。
