# 09-4 USART 串口数据包

> [!abstract] 这一集只解决一个问题
> **一次要发好几个字节、甚至每次长度还不一样时，接收方怎么知道「这串数据到哪里算结束」？**
> 
> 答：给数据加**包头**和**包尾**，把「一串数据」变成一个**数据包**；接收方用一个 **3 状态的状态机**（等待包头 → 接收数据 → 等待包尾）把包切出来。
> 
> 本集是**理论集**，只讲格式和思路；真正的代码在下两集（09-5 讲 **9-3 串口收发HEX数据包** 与 **9-4 串口收发文本数据包** 两个工程）。
> 
> 上一集 [[江协STM32 09-3 串口发送与串口发送接收]] ｜ 下一集 [[江协STM32 09-5 串口收发HEX数据包与文本数据包]] ｜ 章索引 [[江协STM32 09 USART串口（章索引）]]

## 1 为什么需要「数据包」

先看 9-2 工程（上一集）的接收方式：`USART1_IRQHandler` 里**每收到一个字节就置一次标志位**，主循环**一个字节一个字节地处理**（见 09-3 笔记第 7 节）：

```text
电脑发：41 42 43        （三个字节，先后到达）
单片机：收到 0x41 → 处理一次
        收到 0x42 → 处理一次
        收到 0x43 → 处理一次
```

这套办法在「单个字节控制」时够用（发一个字符控制一个 LED），但它**没有「这一批数据从哪开始、到哪结束」的概念**。一旦需求变成下面这样，就出问题了：

- **一次要发多个数据**：比如「设置电机速度 = 500，方向 = 正转，加速度 = 10」，三个参数必须凑齐才能用，不能来一个用一次。
- **每次长度不定**：比如发一段字符串，有时 3 个字符、有时 20 个字符，接收方怎么知道该等多久才算收完？
- **数据本身可能等于任何值**：如果拿某个字节当「结束符」，而这个值又正好是要发送的数据，就会**误判**。

**解决办法就是「打包」**：给一段数据规定好**固定的头部标志**和**尾部标志**，中间是要传的有效数据。有了包的概念，接收方就能把一串无意义的字节流切成一个个有边界的整体。

> [!note] 「为什么打包」这部分是依据推演，不是课件原文
> 课件 Slide 123 / 124 只画了两种包的**格式图**并标注「固定包长，含包头包尾」「可变包长，含包头包尾」，**没有用文字说明「为什么要打包」**。上面这段动机说明是按 9-2 工程的接收方式与课件给出的包格式反推出来的；老师在视频里的口头表述不在课件文本中，已记入「待核对」。

## 2 先分清「数据模式」：HEX 模式 vs 文本模式

课件 Slide 122 把串口数据分成两种呈现方式：

| 模式 | 别名 | 显示方式 |
| --- | --- | --- |
| **HEX 模式** | 十六进制模式 / 二进制模式 | 以**原始数据**的形式显示 |
| **文本模式** | 字符模式 | 以**原始数据编码后**的形式显示 |

同一个 `0x41` 的两种看法：

```text
发送方                                    接收方
0x41 ──► 编码 ──► 'A'  ──────传输──────► 'A' ──► 译码 ──► 0x41
                 （文本模式看到的是这个）        （HEX 模式看到的是这个）
```

**这个区分贯穿 09-5 两个工程**：

- **HEX 数据包**：包里装的可以是**任意字节值**（`0x00`~`0xFF`），适合传传感器数值、控制指令等；在串口助手里要切到 **HEX 模式**发送和查看。
- **文本数据包**：包里装的是**可读字符**（`LED_ON`、`ABC`），适合人机交互；在串口助手里用**文本模式**发送和查看。

## 3 两种包格式

### 3.1 HEX 数据包（课件 Slide 123）

固定包长（4 个数据字节）：

```text
0xFF | 0x01 | 0x02 | 0x03 | 0x04 | 0xFE
包头            4 个数据           包尾
```

可变包长（第一个包 4 个数据、第二个包 3 个数据）：

```text
0xFF | 0x01 | 0x02 | 0x03 | 0x04 | 0xFE | 0xFF | 0x05 | 0x06 | 0x07 | 0xFE
        数据包 1（4 字节数据）                数据包 2（3 字节数据）
```

### 3.2 文本数据包（课件 Slide 124）

固定包长：

```text
'@' | 'A' | 'B' | 'C' | '\r' | '\n'
包头         3 个字符          包尾（两个字符）
```

可变包长：

```text
'@' | 'A' | 'B' | 'C' | '\r' | '\n' | '@' | 'D' | 'E' | '\r' | '\n'
        数据包 1（3 字符）                数据包 2（2 字符）
```

> [!warning] 文本数据包的包尾是**两个字符**
> 课件画的是 `'\r'` 和 `'\n'` 两个字节（回车 + 换行），**不是一个**。这也是 09-5 文本版状态机需要 3 个状态而不是 2 个的根本原因。

### 3.3 固定包长 vs 可变包长

| | 固定包长 | 可变包长 |
| --- | --- | --- |
| 数据长度 | 每次都一样 | 每次可以不一样 |
| 接收方怎么知道数据收完了 | **数够个数**就知道（也可以等包尾） | **只能靠包尾** |
| 包头包尾 | 含包头包尾 | 含包头包尾 |
| 课件出处 | Slide 123 / 124 上半部分 | Slide 123 / 124 下半部分 |
| 09-5 里的实现 | **9-3 HEX 版**：固定 4 字节数据 | **9-4 文本版**：`@` 开头、`\r\n` 结尾，长度可变 |

> [!tip] 本课程实际用到的是「固定包长 + 含包头包尾」（HEX 版）
> HEX 版工程里数据固定 4 个字节、用 `0xFF` 包头 `0xFE` 包尾；因为长度固定，**数够 4 个就知道该等包尾了**，状态机因此只需要 3 个状态。文本版长度可变，必须靠 `\r\n` 来界定，状态机就变成「等 `@` → 收数据直到 `\r` → 等 `\n`」。

## 4 接收思路：从「搬运」到「状态机」

### 4.1 搬运式接收（只适用于固定包长）

最朴素的想法是：**先等包头，等到之后把后面固定个数的字节挨个搬进数组**。

```text
等待包头 ──► 收到包头 ──► 连续搬运 N 个字节到数组 ──► 置接收完成标志
```

这种做法：

- **优点**：逻辑简单，不需要记「现在处于哪个阶段」。
- **缺点**：只能处理**长度固定**的包；而且包尾往往被忽略，或者要额外判断——一旦中途丢一个字节，整包数据就**错位**，且错位后无法自行纠正。

课件 Slide 123 里 HEX 数据包同时画了「固定包长」和「可变包长」两种，说明**长度可变的场合搬运式就不够用了**。

### 4.2 状态机接收（课件的通用做法）

课件 Slide 125（HEX）和 Slide 126（文本）给出的都是**状态机**方案：把接收过程拆成几个**状态**，每来一个字节，先看「现在处于哪个状态」，再决定对这个字节做什么，以及要不要跳到下一个状态。

**HEX 数据包接收（Slide 125 原文标注）：**

| 状态 | 名称 | 收到什么 | 做什么 / 跳到哪 |
| --- | --- | --- | --- |
| `S = 0` | **等待包头** | 收到 `0xFF` | 进入 `S = 1`，数据位置归零 |
| `S = 0` | 等待包头 | 收到**其他数据** | 留在 `S = 0`（丢弃） |
| `S = 1` | **接收数据** | 未收够 4 个数据 | 存入数组，留在 `S = 1` |
| `S = 1` | 接收数据 | 收够 4 个数据 | 进入 `S = 2` |
| `S = 2` | **等待包尾** | 收到 `0xFE` | 回到 `S = 0`，**一包接收完成** |
| `S = 2` | 等待包尾 | 收到**其他数据** | 留在 `S = 2`（继续等包尾） |

**文本数据包接收（Slide 126 原文标注）：**

| 状态 | 名称 | 收到什么 | 做什么 / 跳到哪 |
| --- | --- | --- | --- |
| `S = 0` | **等待包头** | 收到 `'@'` | 进入 `S = 1` |
| `S = 0` | 等待包头 | 收到**其他数据** | 留在 `S = 0` |
| `S = 1` | **接收数据等待包尾** | 收到 `'\r'` | 进入 `S = 2` |
| `S = 1` | 接收数据等待包尾 | 收到**其他数据** | 存为数据，留在 `S = 1` |
| `S = 2` | **等待包尾** | 收到 `'\n'` | 回到 `S = 0`，**一包接收完成** |
| `S = 2` | 等待包尾 | 收到**其他数据** | 停留在 `S = 2` |

### 4.3 状态机的两条通用规矩

把上面两张表抽象一下，状态机接收就是两句话：

1. **每个状态下，对收到的字节只做两件事**：要么「吃掉」（存起来/丢弃），要么「改变状态」。
2. **状态归 0 的那一刻 = 一包完整接收完成**：此时置标志位，通知主循环来取。

```text
        ┌──────────────── 收到包头 ────────────────┐
        │                                          ▼
     S = 0 等待包头                          S = 1 接收数据
        ▲                                          │
        │                                     收够长度 / 收到 '\r'
        │                                          ▼
        └──────────── 收到包尾 ──────────────  S = 2 等待包尾
```

> [!warning] 「收到其他数据」这一格最容易写漏
> 三张状态里，**只有「等待包头」和「等待包尾」两处允许「不匹配就原地不动」**；「接收数据」状态必须把**任何**字节都当数据存下来（除了约定的结束标志）。写代码时如果忘了处理「不匹配」的分支，状态机会卡死或者错位，具体踩法见下一篇的「易错点」。

## 5 校验、出错处理与超时

这三个是「正经通信协议」里常见的手段，本文按核对原则**明确标注出处情况**：

| 手段 | 作用 | 官方材料中的情况 |
| --- | --- | --- |
| **校验**（如累加和校验、CRC） | 在包尾前再加一两个字节，接收方算一遍比对，判断数据在传输中有没有出错 | **官方资料中未见**——课件 Slide 108~126 与两个工程源码里都**没有**校验字段；官方 HEX 包就是「`0xFF` + 4 字节数据 + `0xFE`」，不含校验 |
| **出错处理** | 校验失败时丢弃整包 / 请求重发 | **官方资料中未见** |
| **超时** | 包收到一半卡住了，超过一定时间就复位状态机，避免永远等下去 | **官方资料中未见**——官方状态机**没有超时机制**，`S = 2` 等不到 `0xFE` 就会一直等 |

> [!warning] 本课程的数据包是「教学最小可用版」
> 官方工程的做法是：**只要包头包尾对上就认为收到了一包**，不做校验、不做重发、不做超时。这在课堂实验（短线、低速 9600、无干扰）里没问题，但**不能直接当成可靠协议用**。
> 
> 本页**不替官方补一套校验算法**——课程资料里没有给出具体实现，写了就成了「看起来合理的推测」。这三条只作为**思路提示**保留，已记入「待核对」。

## 6 与上一集「单个字节接收」的对比

| | 09-3 的单个字节接收（9-2 工程） | 09-4/09-5 的数据包接收（9-3、9-4 工程） |
| --- | --- | --- |
| 每次处理的数据量 | **1 个字节** | **一整包**（HEX 版含包头包尾共 6 字节；文本版长度可变） |
| 有没有边界概念 | **没有**，来一个处理一个 | **有**，靠包头包尾界定 |
| 接收变量 | `Serial_RxData`（一个 `uint8_t`） | `Serial_RxPacket[]`（一个数组） |
| 标志位含义 | 「收到了**一个字节**」 | 「收到了**一个完整的包**」 |
| 中断里的逻辑 | 读数据 → 置标志（两步） | 读数据 → **按状态机分派处理** → 需要时才置标志 |
| 需不需要记住上下文 | 不需要（每个字节独立） | **必须**记住（`RxState` 记住阶段、`pRxPacket` 记住收到第几个） |
| 长度可变支持 | 天然支持（本来就一字节一字节） | 固定包长版靠计数，可变包长版靠包尾 |
| 主循环怎么用 | 每字节都处理 | `Serial_GetRxFlag() == 1` 才处理，一次处理一整包 |

**关键差别就一个词：状态。** 单个字节接收是「无状态」的，数据包接收是「有状态」的——所以 09-5 里必须在中断函数里写 `static` 变量来跨中断保存状态。

## 易错点

- [ ] 以为「包头包尾」是随便挑的 → 它们必须是**数据里不会出现的值**，否则会被误判成边界。文本包用 `@` 和 `\r\n` 正是这个原因。
- [ ] 把文本数据包的包尾当成**一个**字符 → 是 `'\r'` **和** `'\n'` **两个**字节，状态机要单独一个状态等第二个包尾。
- [ ] 只在「等待包头」和「接收数据」里写判断，忘了「等待包尾」状态 → 包永远收不完。
- [ ] 状态机里漏掉「收到其他数据」分支 → 状态卡死或错位（比如 HEX 版 `S = 0` 收到非 `0xFF` 时不丢弃，就会把普通数据当成包头开始接收）。
- [ ] 用**搬运式**去接**可变包长**的包 → 长度对不上，数据错位。
- [ ] 把「固定包长」理解成「不用包尾」→ 课件 Slide 123/124 明确写的是「固定包长，**含包头包尾**」。
- [ ] 以为官方工程里有**校验/超时** → 没有；官方包就是「包头 + 数据 + 包尾」三部分。
- [ ] 串口助手模式选错（HEX 包用文本模式发、或反之）→ 看到的字节和协议对不上，白白排查半天。
- [ ] 把 `'\r'`、`'\n'` 当成可打印字符 → 它们在串口助手里看不见（表现为换行），HEX 模式下是 `0D`、`0A`。

## 自测

1. 为什么不直接用「单个字节接收」而要定义数据包？举一个单字节接收处理不了的需求。
2. 课件里 HEX 数据包和文本数据包分别用什么做包头、什么做包尾？各自是几个字节？
3. `S = 0 / S = 1 / S = 2` 三个状态分别叫什么？文本数据包接收的状态机的 `S = 2` 是在等什么？
4. 状态机接收时，「一包接收完成」是在哪个时刻判定的？
5. 为什么本集的数据包接收需要 `static` 变量，而上一集的单字节接收不需要？

> [!success]- 参考答案
> 1. 因为单字节接收**没有边界概念**，无法表达「这几个字节属于同一次发送」。处理不了的需求例如：一次下发「速度、方向、加速度」三个参数，必须凑齐才能执行；或者发送长度每次都不一样的字符串。
> 2. HEX 数据包：包头 **`0xFF`**、包尾 **`0xFE`**（各 1 字节）。文本数据包：包头 **`'@'`**（1 字节）、包尾 **`'\r'` + `'\n'`**（2 字节）。
> 3. `S = 0` **等待包头**、`S = 1` **接收数据**（文本版课件写作「接收数据等待包尾」）、`S = 2` **等待包尾**。文本版的 `S = 2` 在等**第二个包尾 `'\n'`**（第一个包尾 `'\r'` 已经在 `S = 1` 里收掉了）。
> 4. 在**状态回到 `S = 0` 的那一刻**：HEX 版是 `S = 2` 收到 `0xFE` 时，文本版是 `S = 2` 收到 `'\n'` 时。此时才把「接收完成」标志位置 1。
> 5. 因为状态（收到第几个字节、现在处于哪个阶段）必须**跨多次中断调用保存下来**，而每次进中断函数，局部变量都会被重新创建。用 `static` 修饰后变量只初始化一次、内容在多次调用之间保持（`RxState`、`pRxPacket` 就是这么用的，见 09-5 笔记）。
