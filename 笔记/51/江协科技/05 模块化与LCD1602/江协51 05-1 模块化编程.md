# 05-1 模块化编程

> [!abstract] 这一集只解决一个问题
> **怎么把越来越长的代码组织成多个文件，方便复用和维护？**
>
> 一句话：把功能拆成"模块"——每个模块一个 `.c`（实现）+ 一个 `.h`（声明），用 `#ifndef` 防止重复包含。这样 Delay、Nixie 等通用功能写一次，后面每章直接 `#include` 复用。
>
> 这一集是**从"写程序"到"写工程"的分水岭**。它背后是 C 语言的编译链接模型，理解了 `.h/.c` 的关系，后面所有多文件工程（LCD、矩阵键盘、DS1302、红外……）都是一样的套路。
>
> 下一集 [[江协51 05-2 LCD1602调试工具]] ｜ 章索引 [[江协51 05 模块化与LCD1602（章索引）]]

## 1 为什么要模块化

到第 4 章为止，所有代码都塞在一个 main.c 里。随着功能变多（延时、数码管、按键、液晶……），会出现两个问题：

1. **main.c 越来越长、越来越乱**，改一个功能要在一大坨代码里找半天。
2. **每做一个新工程都要重抄一遍**延时函数、数码管函数——代码无法复用。

模块化 = 把通用功能抽出来单独放，以后直接"拿来用"：

```text
  单个 main.c（旧）              多个模块（新）
  ┌──────────────┐         ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ main.c        │         │ Delay.c/h │ │ Nixie.c/h │ │ main.c    │
  │ + 延时函数     │   →     │ 延时模块   │ │ 数码管模块 │ │ 主程序    │
  │ + 数码管函数   │         └──────────┘ └──────────┘ └──────────┘
  └──────────────┘
```

> [!note] 模块化的三大收益
> 1. **复用**：Delay、Nixie 写一次，第 6、7、8……章直接 `#include` 拿来用，不用重抄。
> 2. **可维护**：改延时逻辑只动 Delay.c，不影响别的。
> 3. **可读性**：main.c 只保留主流程，一眼看清"在干什么"。

## 2 理解 .h 和 .c 的分工（编译链接的底层）

要真正理解模块化，先明白 C 程序是怎么从"多个源文件"变成"一个可执行文件"的：

```text
  多个 .c 文件 ──编译──► 多个 .o 目标文件 ──链接──► 一个 .hex 可执行文件
  Delay.c      →      Delay.o
  Nixie.c      →      Nixie.o      ──┐
  main.c       →      main.o      ──┼──► 最终 hex（链接器把所有 .o 合起来）
                                    │
  （编译阶段各自独立）                （链接阶段拼装 + 解析函数引用）
```

关键点：**编译是"各自独立"的**。编译 `main.c` 时，编译器**看不到** `Delay.c` 的内容，它只知道 `main.c` 里调用了 `Delay(20)` 这个函数。那编译器怎么知道 `Delay` 的参数类型、返回类型对不对？

**答案：靠 `.h` 头文件里的"函数声明"（原型）**。

```c
void Delay(unsigned int xms);   // 函数声明：告诉编译器"Delay 长这样"
```

- **`.h`（头文件）= 接口说明书**：声明"这个模块有哪些函数、参数和返回值是什么类型"。给**调用方**（main.c）看。
- **`.c`（源文件）= 具体实现**：函数到底怎么干。给**编译器/链接器**看。

所以 `.h` 和 `.c` 的关系是：

```text
  Delay.h（声明）                 Delay.c（实现）
  ┌──────────────────┐          ┌──────────────────┐
  │ void Delay(xms); │  ←接口→  │ void Delay(xms){  │
  │                  │    │     │   ...具体实现...  │
  └──────────────────┘    │     └──────────────────┘
        ▲                 │
        │ main.c 通过 include 看到声明，
        │ 从而知道 Delay 怎么调用
        │（链接时再由链接器把 main.o 和 Delay.o 拼起来）
```

> [!tip] 一句话理解 .h 和 .c
> **`.h` 是"菜单"（告诉你能点什么菜），`.c` 是"后厨"（菜具体怎么做）**。调用方看菜单点菜，不用管后厨怎么做；后厨换了做法（改 .c），菜单不变（.h 不变），调用方无感。

## 3 模块的组成

每个模块由两个文件组成：

| 文件 | 内容 | 作用 |
| --- | --- | --- |
| `Delay.h` | 函数**声明** | 告诉别人"这个模块提供哪些函数" |
| `Delay.c` | 函数**实现** | 具体怎么干 |

### 3.1 Delay.h（声明）

```c
#ifndef __DELAY_H__
#define __DELAY_H__

void Delay(unsigned int xms);   // 只声明，不实现（结尾是分号，没有函数体）

#endif
```

### 3.2 Delay.c（实现）

```c
#include "Delay.h"   // .c 也要包含自己的 .h，保证声明和实现一致

//延时子函数
void Delay(unsigned int xms)
{
	unsigned char i, j;
	while(xms--)
	{
		i = 2;
		j = 239;
		do
		{
			while (--j);
		} while (--i);
	}
}
```

> [!warning] `.c` 文件也要 `#include` 自己的 `.h`
> 这是新手常漏的一点。`.c` 包含自己的 `.h` 有两个好处：
> 1. 编译器能检查"声明"和"实现"是否一致（参数类型、返回值对不上会报错）。
> 2. `.h` 里如果有宏定义、类型定义，`.c` 里也能用到。

## 4 头文件保护（#ifndef）

`#ifndef / #define / #endif` 这套叫**头文件保护（include guard）**，防止同一个头文件被多次包含导致"重复定义"：

```c
#ifndef __DELAY_H__   // 如果没有定义过 __DELAY_H__
#define __DELAY_H__   // 就定义它

void Delay(unsigned int xms);

#endif                // 结束
```

工作原理：

- 第一次包含：`__DELAY_H__` 没定义 → 定义它，中间内容生效。
- 第二次（及以后）包含：`__DELAY_H__` 已定义 → `#ifndef` 为假，中间内容被跳过。

> [!note] 为什么会"重复包含"
> 假设 `a.h` 和 `b.h` 都包含了 `Delay.h`，而 `main.c` 又同时包含 `a.h` 和 `b.h`。这样 `Delay.h` 就被"间接"包含了两次，`void Delay(...)` 声明出现两次。虽然函数声明重复通常无害，但**宏定义、结构体定义、全局变量定义重复就会出现"重复定义"错误**。所以加保护是最稳妥的习惯。

> [!tip] 保护宏的命名习惯
> 一般用"模块名大写 + 前后下划线"，如 `__DELAY_H__`、`__NIXIE_H__`。只要全项目唯一即可（避免两个模块用了同一个宏名互相干扰）。

## 5 怎么用模块

在 main.c 里 `#include` 模块头文件：

```c
#include <REGX52.H>
#include "Delay.h"	//包含Delay头文件
#include "Nixie.h"	//包含数码管头文件

void main()
{
	while(1)
	{
		Nixie(1,1);
		Nixie(2,2);
		Nixie(3,3);
		Nixie(4,4);
		Nixie(5,5);
		Nixie(6,6);
	}
}
```

> [!note] 双引号 vs 尖括号
> - `#include "Delay.h"`（**双引号**）→ 先在**当前目录**（工程目录）找，用于**自己的模块**。
> - `#include <REGX52.H>`（**尖括号**）→ 在**系统/编译器库目录**找，用于**系统头文件**。
>
> 自己的模块用 `""`，系统的用 `<>`，别搞混。

## 6 完整模块清单（本集）

本集把第 4 章的延时和数码管拆成了两个模块：

- `Delay.h` / `Delay.c`：延时函数 `Delay(xms)`。
- `Nixie.h` / `Nixie.c`：数码管显示 `Nixie(Location, Number)`（内含段码表和位码）。

Nixie.c 的内容和第 4 章一样，只是抽到了独立文件里，main.c 只负责调用。

> [!tip] 模块化的"进化路线"
> 到这一步，你应该建立一个习惯：**做完一个功能就把它封装成模块**。后面矩阵键盘（MatrixKey.c）、LCD1602（LCD1602.c）、DS1302（DS1302.c）、I2C（I2C.c）、单总线（OneWire.c）、红外（IR.c）……全都是"先写模块，再在 main 里调用"。这个思路贯穿第 5 章到第 17 章。

## 7 进阶：static 和 extern（了解即可）

模块化到后面会遇到两个关键词，提前了解：

| 关键词 | 作用 | 场景 |
| --- | --- | --- |
| `static`（修饰函数） | 函数只在**本文件**可见，别的文件调不到 | 模块内部私有的辅助函数 |
| `extern`（修饰变量） | 声明一个**别的文件定义**的全局变量 | 跨文件共享一个全局变量 |

```c
// 某模块 .c 里
static void Helper(void);   // 只在当前 .c 里能用的"私有"函数

// 别的文件想用 main.c 里定义的全局变量
extern unsigned char LEDNum;   // 声明"LEDNum 在别处定义了"
```

本课官方源码用得不多，但理解这两个词能让模块化更规范。第 6 章矩阵键盘的 `MatrixKey.c` 就是一个典型模块。

## 8 易错点

- [ ] `.c` 忘了 `#include` 自己的 `.h` → 声明和实现可能不一致，编译器查不出来。
- [ ] 头文件没加 `#ifndef` 保护 → 重复包含报"重复定义"错误。
- [ ] 用 `<>` 包含自己的模块 → 找不到，应改用 `""`。
- [ ] 在 `.h` 里写函数实现（而非声明）→ 被多个文件包含时会重复定义（除非加 static）。
- [ ] 改了模块但没重新编译 → Keil 未检测到变化，现象没更新（可手动 Rebuild）。
- [ ] 只写了 `.c` 没写 `.h` → 别的文件调用不到这个模块。

> [!success]- 参考答案
> 1. `.h` 放函数声明（接口），`.c` 放函数实现（具体逻辑）。
